## Verified locally

Keycloak is running in a local Docker container, published only on
`127.0.0.1:8843`. It uses a pinned SUSE BCI OpenJDK image and a Keycloak
distribution verified against the SHA256 digest on its upstream release.

The test performs password login for each synthetic user. It does not send
owner/product values in the login request. Keycloak reads those values from
administrator-managed user attributes and inserts them into the signed SAML
response through the configured mappers.

| User | Automatically assigned owner | Automatically assigned product | Signed response verified |
| --- | --- | --- | --- |
| Alice | `lab-sso-alice` | `lab-sso-product-a` | Yes |
| Bob | `lab-sso-bob` | `lab-sso-product-b` | Yes |
| Untagged | Absent | Absent | Yes |

The verifier checks the metadata signing certificate, issuer, audience, NameID
and attribute values. Keycloak's persisted user-profile configuration restricts
editing `owner`/`product` to administrators.

Sanitized evidence is saved in `artifacts/sso-idp/login-verification.json`.
SAML assertions, passwords and tokens are not included in committed evidence.

## Prepared AWS configuration

The `sso-lab/` Terraform root declares three matching Identity Center users,
one shared `BedrockCostLab` permission set, a model-scoped inline policy, the
attribute configuration, and three member-account assignments.

Terraform initialization and validation passed. The initial live plan stopped
with the missing-instance precondition. A subsequent read-only check confirmed
the console-created organization instance is active in Frankfurt. The SSO
Terraform root has not been applied.

The console rejected the original metadata with “url validation failed.”
It advertised `https://localhost:8843` for the issuer and all service endpoints.
The non-FQDN hostname is the leading explanation; AWS has not confirmed the
exact validation rule.

Keycloak now advertises `https://bedrock-idp.127.0.0.1.sslip.io:8843`. Its TLS
certificate, preview client, metadata and signed assertion issuer agree.
All three login checks passed after the change, and the password-file digest
and metadata signing certificates matched their pre-migration values.
Only the container and its TLS certificate were replaced; its database remains.

Public DNS returns loopback for this hostname, but the local resolver did not
return an address. The scripts connect directly to loopback while verifying TLS
for the hostname. Browser testing may require the hosts-file entry in the
[runbook](../sso-idp/README.md).

Replacement metadata is at `artifacts/sso-idp/idp-metadata.xml`. Re-upload it in
the console and confirm acceptance before considering the URL issue resolved.
The runbook also gives the AWS service-provider metadata download location.
